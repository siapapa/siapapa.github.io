# 23H · 최종 튜닝 & 리허설

## 학습목표

- 발표 슬라이드 3장을 완성할 수 있다
- 라이브 데모의 리스크를 점검하고 대비할 수 있다
- 5~7분 발표를 리허설할 수 있다

!!! tip "🧭 이 시간을 이렇게 읽으세요 (비개발자용)"
    - **한 줄 핵심**: 어제까지의 평가 결과를 보고 약점 1~2개를 골라 손보고, 5~7분 발표 슬라이드를 준비합니다.
    - **꼭 이해**: 모든 메트릭을 동시에 올리려 하지 말고, **가장 낮은 점수 한 개**부터 개선. 슬라이드 3장(문제·아키텍처·평가결과)으로 충분.
    - **지금은 몰라도 OK**: 새로운 기법(Re-rank·HyDE)을 발표 직전에 추가하기 — 시간이 많지 않다면 기존 코드 안정화에 집중.
    - **막히면**: 모르는 단어는 [용어 사전](../appendix/glossary.md) 으로 → 처음이라면 [비개발자 학습 가이드](../beginners-guide.md).

!!! danger "여기서부터는 본인 프로젝트 에이전트로 진행"
    Day 4 21H·22H에서는 설명을 쉽게 하려고 공통 **병원 DB**를 예시로 썼지만, 발표와 최종 제출은 **본인 프로젝트 에이전트**가 기준입니다. 이 시점에 아래를 한 번 체크하세요:

    - [ ] `LANGCHAIN_PROJECT` / `LANGSMITH_PROJECT` 값이 본인 프로젝트 이름(예: `bookshop-agent-final`)으로 설정돼 있다
    - [ ] 21H에서 쌓은 LangSmith 트레이스가 **본인 DB 질문**으로 기록돼 있다
    - [ ] 22H Ragas 평가의 `ground_truths_dict`가 **본인 10개 질문 정답**으로 채워져 있다
    - [ ] 발표용 Before/After 차트(`ragas_before_after.png`)도 본인 에이전트 결과로 갱신돼 있다

    병원 DB 예시 코드는 참고용입니다. 23H 이후 발표·수료는 전부 **본인 프로젝트 에이전트** 기준으로 말해야 합니다.

## 발표 슬라이드 3장 구조

### 슬라이드 1: 문제 정의 (1분)

```
├── 도메인 소개: "나는 ___를 분석하는 에이전트를 만들었습니다"
├── 대상 사용자: "___가 사용합니다"
├── 핵심 질문 유형: "이런 질문에 답합니다: ..."
└── 왜 에이전트인가?: "단순 SQL이 아니라 에이전트가 필요한 이유"
```

**포인트**: 청중이 도메인을 모를 수 있으므로, 1~2문장으로 배경을 설명하세요.

**좋은 예시**:

- "병원 관리자가 매일 반복하는 SQL 쿼리를 자연어로 질문하면 자동으로 답변하는 에이전트입니다."
- "이커머스 팀장이 '이번 달 매출 Top 5 상품은?'처럼 물어보면 실시간으로 DB를 조회합니다."

**나쁜 예시**:

- "SQL 에이전트를 만들었습니다." (너무 일반적 -- 도메인과 사용자가 불명확)

---

### 슬라이드 2: 아키텍처 (1.5분)

```
├── LangGraph 상태 다이어그램 (Mermaid 스크린샷)
├── 데이터 흐름: 스키마 → 검색 → SQL 생성 → 실행 → 검증 → 답변
├── 사용 도구 및 선택 이유
└── 특별히 고민한 설계 포인트 1가지
```

**포인트**: 코드를 줄 단위로 설명하지 말고, **전체 흐름**과 **핵심 설계 결정**을 전달하세요.

**"특별히 고민한 설계 포인트" 예시**:

- "재시도 로직을 넣어서, SQL 오류가 나면 에이전트가 스스로 수정합니다."
- "가드레일을 넣어서, DROP/DELETE 같은 위험한 SQL은 차단합니다."
- "스키마 COMMENT를 상세하게 작성해서, LLM이 컬럼 의미를 정확히 이해하게 했습니다."

---

### 슬라이드 3: 결과 & 회고 (1.5분)

```
├── Ragas Before/After 차트 ← 핵심!
├── 성공 사례 2건 (질문 → SQL → 답변)
├── 실패 사례 1건 + 디버깅 과정
└── 배운 점 / 향후 개선 방향
```

**포인트**: 실패 사례와 디버깅 과정이 발표의 차별점입니다. 완벽한 결과보다 **학습 과정**을 보여주세요.

**실패 사례 설명 예시**:

- "이 질문은 Faithfulness가 0.55였습니다. LangSmith에서 트레이스를 열어보니, LLM이 SQL 결과에 없는 '박준혁 의사'를 답변에 추가했습니다. 프롬프트에 '결과만 사용하세요' 규칙을 추가한 후 0.82로 개선되었습니다."

!!! tip "완벽한 에이전트보다 실패에서 배운 것이 더 중요"
    발표에서 가장 높은 평가를 받는 것은 **100% 성공한 에이전트**가 아닙니다. "이런 문제가 있었고, 이렇게 분석했고, 이렇게 개선을 시도했다"는 **엔지니어링 사고 과정**을 보여주는 발표가 가장 인상적입니다. 실패를 숨기지 말고, 실패에서 배운 것을 당당하게 공유하세요.

## 라이브 데모 리스크 체크리스트

| # | 항목 | 점검 사항 | 상태 |
|---|---|---|---|
| 1 | Colab 런타임 | 살아있는가? (타임아웃 주의) | [ ] |
| 2 | Neon DSN | 유효한가? (세션 만료 확인) | [ ] |
| 3 | OpenAI API Key | 잔액이 남아있는가? | [ ] |
| 4 | LangSmith | 트레이싱이 작동하는가? | [ ] |
| 5 | 데모 질문 | 3~5개를 미리 선정했는가? | [ ] |
| 6 | 백업 스크린샷 | 네트워크 불안정 시 대비했는가? | [ ] |
| 7 | 실패 질문 | 실패하는 질문을 알고 있는가? (설명용) | [ ] |

!!! warning "라이브 데모는 항상 실패할 수 있다"
    라이브 데모는 항상 실패할 수 있습니다. **백업 스크린샷**을 반드시 준비하세요. 데모가 실패해도 스크린샷으로 설명할 수 있으면 감점이 크지 않습니다. "실제로 이렇게 동작합니다"라고 스크린샷을 보여주는 것도 효과적인 발표 기법입니다.

!!! tip "백업 스크린샷 3장 준비하는 법"
    발표 전에 반드시 다음 **3장의 스크린샷**을 준비하세요:

    **1. 에이전트 실행 화면** -- 성공적인 질문 2~3개의 입력과 출력을 캡처합니다. Colab 셀의 실행 결과가 잘 보이도록 스크롤하여 캡처하세요.

    **2. LangSmith 트레이스 화면** -- LangSmith UI에서 Run Tree가 잘 보이는 트레이스를 캡처합니다. 각 노드의 실행 시간과 토큰이 보이면 좋습니다.

    **3. Ragas Before/After 차트** -- `ragas_before_after.png`를 발표 슬라이드에 삽입할 수 있도록 저장합니다. 파일로 저장했으므로 네트워크와 무관하게 사용 가능합니다.

    이 3장이 있으면 네트워크가 끊기거나 Colab이 종료되어도 발표를 완성할 수 있습니다.

## 개인 작업 시간 가이드

!!! warning "23H는 매우 촘촘합니다 -- 사전 완료를 전제로 진행"
    Ragas **v2 재평가**는 LLM 호출 특성상 10문항 기준 2~5분이 실측으로 필요합니다. 여기에 슬라이드 3장 작성, 데모 리허설, 강사 피드백을 전부 50분 안에 쑤셔 넣으면 현실적으로 불가능합니다. 따라서 아래를 **22H 종료 직후~23H 시작 전 쉬는 시간**에 미리 끝내주세요:

    - [ ] v1 리포트(`report`) + `ragas_before_after.png` 생성 완료
    - [ ] v2 프롬프트로 **1회** 재평가까지 돌려 `report_v2` 확보 (선택사항이지만 강력 권장)
    - [ ] 발표 슬라이드 1~2번 틀만 잡아두기

    23H 수업 시간은 아래 **피드백·리허설 중심**으로 사용합니다. 튜닝은 **하나의 개선**만 반영하고 비교하세요 -- 이것저것 동시에 바꾸면 Before/After 해석이 무너집니다.

### 1단계: 최종 튜닝 반영 (15분)

```
할 일:
  □ Ragas 평가 결과에서 가장 낮은 메트릭 1개만 선택
  □ 해당 메트릭의 원인 진단 (22H 진단 코드 참고)
  □ 프롬프트 or 스키마 COMMENT 중 하나만 수정
  □ (선택) v2 재평가 미실행 시 이 블록에서 실행 -- 3~5분 소요 가산
  □ Before/After 1장 차트 확정
```

### 2단계: 발표 슬라이드 마무리 (15분)

```
할 일:
  □ 슬라이드 1: 도메인 + 사용자 + 핵심 질문 유형 작성
  □ 슬라이드 2: LangGraph 다이어그램 스크린샷 삽입
  □ 슬라이드 3: Ragas Before/After 차트 삽입
  □ 슬라이드 3: 성공 사례 2건 + 실패 사례 1건 정리
  □ "한 줄 요약" 작성

  도구: Google Slides, PowerPoint, 또는 Markdown
```

### 3단계: 데모 테스트 + 리허설 (10분)

```
할 일:
  □ 데모할 질문 3~5개 선정 (본인 프로젝트 DB 기준)
  □ 각 질문 실제 실행하여 결과 확인
  □ 실패하는 질문 파악 (설명 준비)
  □ 백업 스크린샷 3장 저장
  □ Colab 런타임 + Neon 연결 상태 확인
  □ 타이머 켜고 1회 리허설 (목표 6분)
```

## 강사 1:1 피드백 (수강생당 3~5분, 병렬 진행)

수강생 수가 많으면 강사는 **위 개인 작업 시간과 병렬**로 1:1 피드백을 돌립니다. 피드백 대기 중에는 피어 리허설을 진행하세요.

강사가 각 수강생을 방문하여 아래 체크리스트를 확인합니다.

```
강사 체크리스트:
  □ 에이전트가 정상 동작하는가? (기본 질문 1개 실행)
  □ LangSmith 트레이스가 기록되고 있는가?
  □ Ragas 리포트가 준비되었는가?
  □ 발표 흐름이 자연스러운가?
  □ 라이브 데모 리스크가 관리되고 있는가?
  □ 발표 시간이 7분 이내인가?
```

!!! tip "강사 피드백 활용법"
    강사 피드백에서 받은 조언을 바로 적용하세요. 특히:

    - "발표가 너무 길다" → 슬라이드 1의 배경 설명을 줄이세요
    - "데모가 불안하다" → 백업 스크린샷을 더 준비하세요
    - "회고가 얕다" → 실패 원인을 더 구체적으로 분석하세요
    - "에이전트가 불안정하다" → 안정적인 질문 위주로 데모 질문을 변경하세요

## 실습 과제

!!! example "실습 -- 발표 리허설 1회"
    1. **타이머를 켜고** 발표 스크립트를 읽으며 시간을 측정하세요.
    2. 7분을 초과하면 어디를 줄일지 메모하세요.
    3. 6분 미만이면 데모 질문을 1개 추가하거나, 회고를 더 깊이 설명하세요.
    4. 가능하면 **옆 사람에게 한 번 발표**해보세요 -- 청중의 반응을 보면 어디가 지루하고 어디가 인상적인지 알 수 있습니다.

    **리허설 체크리스트:**

    - [ ] 총 소요 시간: ___ 분 ___ 초
    - [ ] 데모가 정상 작동했는가?
    - [ ] 발표 흐름이 자연스러웠는가?
    - [ ] "한 줄 요약"이 인상적이었는가?

!!! question "생각해보기"
    - 발표에서 가장 전달하고 싶은 **한 가지 메시지**는 무엇인가요?
    - 청중이 발표를 듣고 "이 사람은 ___를 잘한다"고 느끼게 하려면 어떤 부분을 강조해야 할까요?
    - 데모가 실패하면 어떻게 대처할 것인가요? 미리 대사를 준비해두세요.

## 발표 실패 시 대응 가이드

라이브 데모에서 문제가 발생했을 때, 당황하지 말고 아래와 같이 대응하세요.

### Colab 런타임이 종료된 경우

```
대사 예시:
"런타임이 종료되었네요. 미리 준비한 스크린샷으로 보여드리겠습니다.
이 화면이 실제 실행 결과입니다. [스크린샷 전환]"
```

### API 호출이 실패한 경우

```
대사 예시:
"네트워크 문제로 API 응답이 늦어지고 있습니다.
이 질문은 평소에 이런 결과를 반환합니다. [스크린샷 전환]
실패 원인을 분석해보면..."
```

### SQL 오류가 발생한 경우

```
대사 예시:
"지금 SQL 오류가 발생했는데, 실제로 이런 오류는 에이전트 개발에서 자주 만납니다.
LangSmith에서 이 트레이스를 보면 [스크린샷 전환] 어디서 실패했는지 바로 확인할 수 있습니다.
이것이 LangSmith의 가치입니다."
```

!!! tip "실패를 기회로 바꾸기"
    데모 실패는 오히려 **LangSmith의 가치를 보여줄 기회**입니다. "이런 오류가 발생했을 때, LangSmith 트레이스에서 원인을 이렇게 찾았습니다"라고 설명하면, 단순한 성공 데모보다 더 인상적인 발표가 됩니다.

### 진행 방법

1. 2인 1조로 짝을 이룹니다
2. A가 먼저 발표합니다 (7분 타이머)
3. B가 피드백합니다 (2분):
    - "가장 인상적이었던 부분은..."
    - "이 부분은 좀 더 명확하면 좋겠어요..."
    - "시간은 적절했나요?"
