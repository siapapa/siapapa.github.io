# 23H · 최종 튜닝 & 발표 준비

개인 작업 시간입니다. 강사가 순회하며 1:1 로 봅니다.

---

## 체크포인트

발표 전에 이것들이 되는지 확인하세요.

- [ ] **학습된 정책이 있고 `--gui` 로 눈으로 확인했는가**
- [ ] **성공 기준을 자기 과제에 맞게 정의했는가** (임시 기준 그대로면 감점)
- [ ] 비전 모델의 **운영 지표**(불량 유출·과검)를 냈는가
- [ ] 결과가 DB 에 들어가 있고 **자연어로 물어볼 수 있는가**
- [ ] **한계**를 스스로 말할 수 있는가

!!! danger "눈으로 확인하지 않은 정책은 발표하지 마세요"
    곡선이 올라갔다고 잘하는 것이 아닙니다.
    보상 해킹을 발견하는 유일한 방법은 **실제 동작을 보는 것**입니다.

---

## 슬라이드 3장

| 장 | 내용 | 담을 것 |
|---|---|---|
| **1. 문제** | 무엇을 하려 했나 | 시나리오, 왜 이것인가 |
| **2. 아키텍처** | 어떻게 만들었나 | 환경 정의, 보상 설계, 데이터 흐름 |
| **3. 결과** | 무엇을 얻었나 | 성공률, 운영 지표, **한계** |

### 2장에 반드시 넣을 것 — 보상 설계 근거 ★

```
주 보상    목표 거리 exp(-d²/σ²)        가중치 2.0
정규화     관절 속도 페널티              -1e-4
          행동 변화율 페널티            -1e-3
          관절 한계 페널티              -0.1

왜 이렇게: 처음에 action_rate 를 뺐더니 로봇이 떨면서 목표에 접근했고,
          실제 로봇에 옮기면 위험하다고 판단해 다시 넣었습니다.
```

!!! success "이런 문장이 있으면 좋은 발표입니다"
    "해 봤더니 이랬고, 그래서 이렇게 바꿨습니다."

### 3장에 반드시 넣을 것 — 한계

- 합성 데이터만으로 학습했다는 것
- 부품 형상이 실제와 다르다는 것
- 실제 로봇 검증이 남았다는 것
- sim2real 갭이 어디서 올 것으로 예상하는지

## 시간이 부족하다면

우선순위입니다.

1. **정책이 돌아가는 것** — 완벽하지 않아도 동작하면 됩니다
2. **성공 기준 정의** — 임시 기준을 그대로 두지 마세요
3. 자연어 질의 데모
4. 비전 모델

!!! tip "완성도보다 설명 가능성입니다"
    절반만 됐어도 **왜 거기까지밖에 못 했는지** 설명할 수 있으면
    다 만들고 설명 못 하는 것보다 낫습니다.

---

## 자주 나오는 질문

**Q. 학습이 끝까지 수렴하지 않았습니다.**
곡선과 진단 결과를 보여 주고, 다음에 무엇을 바꿀지 말하면 됩니다.
수렴 못 한 이유를 아는 것이 수렴시킨 것만큼 중요합니다.

**Q. 성공률이 낮습니다.**
낮은 것 자체는 문제가 아닙니다. **왜 낮은지** 를 설명하세요.
보상 설계 문제인지, 과제가 어려운지, 학습 시간이 부족했는지.

**Q. 자연어 질의에 쓸 데이터가 부족합니다.**
Day 2 의 학습 로그만 있어도 됩니다. 여러 조건으로 돌린 것이 있으면
비교 질의가 의미를 가집니다.
