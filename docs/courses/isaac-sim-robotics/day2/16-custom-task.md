# 16H · 커스텀 태스크 — 자기 시나리오로

!!! warning "이 시간의 실습은 최종 검증 전입니다"

## 학습 목표

- 자기 시나리오를 태스크로 옮긴다
- 막히는 지점을 미리 안다

---

## 절차

```
1. 19_sorting_env.py 를 복사 → my_task_env.py
2. 씬       — 필요한 물체를 SceneCfg 에 추가
3. 관측     — 정책이 알아야 할 것을 ObservationsCfg 에
4. 행동     — 무엇을 시킬지 ActionsCfg 에
5. 보상     — 주 보상 하나 + 정규화 항 몇 개
6. 종료     — time_out + 실패 조건
7. 단독 실행해 환경이 만들어지는지 확인 (무작위 행동)
8. 20_train.py 의 load_env_module() 경로를 내 파일로 바꿔 학습
```

!!! tip "7번을 건너뛰지 마세요"
    무작위 행동으로 몇 스텝 돌려 보면 환경 자체의 문제를
    학습 전에 잡을 수 있습니다. 학습을 걸고 30분 뒤에 발견하면 손해입니다.

---

## 흔한 막힘

| 증상 | 원인 |
|---|---|
| 환경 생성에서 죽음 | 자산 경로 / `{ENV_REGEX_NS}` 누락 |
| 관측 차원이 예상과 다름 | 항 스케일·concatenate 설정 |
| **보상이 항상 0** | 보상 함수의 `params` 이름 오타 — **조용히 실패** |
| 학습이 정체 | 목표 정보가 관측에 없음 (11H 원칙 ①) |
| 학습이 시작조차 안 됨 | 종료 조건 없음 |

!!! danger "보상이 항상 0 인 경우가 가장 찾기 어렵습니다"
    `params` 딕셔너리의 키 이름을 틀리면 에러 없이 기본값이 쓰이거나
    항이 무시됩니다. **항을 하나씩 켜 가며** 확인하세요.

## 범위를 분명히 합니다

!!! note "16H 안에 완성되는 사람은 거의 없습니다"
    목표는 **"환경이 만들어지고 학습이 시작되는 것"** 까지입니다.
    수렴은 과제로 이어집니다.

    학습을 걸어 두고 Day 3 로 넘어가세요.

## Direct workflow — 참고

Manager-based 가 답답해지면 Direct 방식도 있습니다.

| | Manager-based | Direct |
|---|---|---|
| 구성 | 항으로 선언 | 클래스 메서드로 구현 |
| 진단 | 쉬움 | 직접 로그를 심어야 |
| 자유도 | 프레임워크 범위 안 | 높음 |
| 성능 | 충분 | 튜닝 여지 큼 |

**처음에는 Manager-based 가 낫습니다.** 구조가 잡혀 있어야
"무엇이 문제인지" 를 좁힐 수 있습니다.

## 과제 #2 — Day 3 시작 시 제출

1. **커스텀 태스크 정의 파일**

!!! success "3번이 배점의 핵심입니다"
    곡선이 잘 올라간 것보다, **왜 그렇게 설계했는지 설명할 수 있는 쪽**이
    현장에서 쓸모 있습니다.

    "이 항을 뺐더니 이렇게 됐고, 그래서 다시 넣었습니다" —
    이런 문장이 있으면 좋은 리포트입니다.
