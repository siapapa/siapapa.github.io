# 5H · 카메라 센서

!!! warning "이 시간의 실습은 최종 검증 전입니다"
    특히 어노테이터 추가 메서드 이름이 버전에 따라 다를 수 있습니다.
    스크립트는 실패해도 죽지 않고 건너뛰도록 만들어 두었습니다.

**실습 스크립트**: `course_b/day1/13_sensors_camera.py`

## 학습 목표

- 카메라 → 렌더 프로덕트 → 어노테이터 경로를 이해한다
- RGB 말고 무엇을 뽑을 수 있는지 안다
- **렌더링 비용**을 숫자로 감 잡는다

---

## 데이터 경로 — 센서는 다 같습니다 ★

```
USD Camera 프림   →  Render Product  →  Annotator  →  get_data() → numpy
"어디서 보는가"      "몇 픽셀로"        "무엇을 뽑을까"
```

**LiDAR 도 IMU 도 구조가 같습니다.** 프림을 만들고, 무엇을 뽑을지 붙이고, 읽습니다.
이 틀을 잡아 두면 다음 시간이 쉽습니다.

## 무엇을 뽑을 수 있나

| 어노테이터 | 무엇 | 쓰는 곳 |
|---|---|---|
| `rgb` | 컬러 이미지 | 기본 |
| `distance_to_camera` | 깊이 | 3D 인식·거리 측정 |
| `semantic_segmentation` | 픽셀별 클래스 | **학습 라벨** |
| `bounding_box_2d_tight` | 물체 박스 | **검출 학습 라벨** |
| `normals` | 표면 법선 | 재질·조명 분석 |

**한 번 렌더하면 이 모두를 동시에 얻을 수 있습니다.**
현장 카메라로는 불가능한 일이고, 합성 데이터의 가장 큰 장점입니다.

---

## 배치와 초기화

```python
camera = api.Camera(
    prim_path="/World/Cameras/Inspection",
    position=np.array([0.0, -2.5, 2.0]),
    frequency=20,
    resolution=(640, 480),
)

world.reset()
camera.initialize()        # ← 이걸 빼먹으면 빈 배열이 돌아옵니다
```

!!! danger "`initialize()` 를 빼먹으면"
    `get_rgba()` 가 **빈 배열**을 돌려줍니다. 에러가 안 나서 원인을 찾기 어렵습니다.

    ```
    프레임 0: 빈 데이터 — camera.initialize() 를 불렀는지 확인
    ```

!!! tip "기초 과정에서 잡아 둔 카메라 자리"
    `SmartFactory-01` 의 검사 스테이션 카메라와 같은 위치입니다.
    그때 배치해 둔 것이 여기서 그대로 쓰입니다.

## 워밍업 — 첫 프레임을 버리세요 ★

```python
for _ in range(30):
    world.step(render=True)      # 이 프레임들은 버립니다
```

!!! danger "첫 몇 프레임은 검게 나오거나 노이즈가 낍니다"
    렌더가 아직 안정되지 않은 상태입니다.
    **그대로 데이터셋에 섞으면 학습이 망가집니다.**

    8H 의 품질 검수에서 이 문제가 실제로 잡힙니다 —
    "검은 프레임 10.1%" 같은 결과가 나옵니다.

---

## 렌더링은 공짜가 아닙니다

스크립트가 프레임당 소요시간과 1,000장 예상 시간을 출력합니다.

```
10프레임 저장 → .../\_out/camera
소요 2.31초 · 프레임당 231ms (4.3 fps)
→ 이 속도면 1,000장에 약 3.9분 걸립니다.
  7H 데이터셋 실습에서 생성량을 정할 때 이 숫자를 쓰세요.
```

| 늘리면 | 비용 |
|---|---|
| 해상도 2배 (640→1280) | 픽셀 수 4배 |
| 어노테이터 추가 | 종류당 추가 렌더 패스 |
| 프레임 수 | 선형 증가 |

**해상도와 프레임 수의 곱**으로 비용이 늘어납니다.
8H 에서 1,000장을 만들 때 이 감각이 필요합니다.
